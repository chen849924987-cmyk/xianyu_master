# 测试目录是干什么的？（尽量白话）

如果你不想先看很长的架构文档，只看这一份就够建立直觉。另一份更细的说明在 **[ARCHITECTURE.md](./ARCHITECTURE.md)**。

---

## 一句话

**`tests/` 不再让 Playwright Test 自动「批卷子」**：**离线检查**交给一个小脚本；**要点浏览器的地方**交给 **Cursor 里的 AI + Playwright MCP** 按 markdown 清单执行。

---

## 为什么要分好几个文件夹？

| 文件夹 | 比喻 | 实际干啥 |
|--------|------|----------|
| **`mcp/features/`** | **真网实验手册** | 一页一个 Feature：打开谁、点哪里、期望看见什么；AI 拿着 MCP 按步骤做。 |
| **`mcp/protocols/`** | **进场检查单** | 不用浏览器时怎么验收（例如对照注册表与 `dist`）；AI 先跑脚本再记结论。 |
| **`mcp/scripts/`** | **自动判定器** | `verify-offline.ts` 把「登录墙 URL 判对了没」「注册表齐不齐」一次跑完。 |
| **`pure/`** | **例题数据表** | 例如一堆 URL + 期望算不算登录墙；脚本逐行核对。 |
| **`actions/`** | **标准动作说明** | 页面流程的人类可读封装，可与 CLI / MCP 步骤对照。 |
| **`support/`** | **工具间** | 找仓库根、子进程测环境变量等。 |

---

## 你平时怎么做？（最小流程）

1. 仓库根目录 **`npm run test`**  
   - 会先 **`npm run build`**，再跑 **`tests/mcp/scripts/verify-offline.ts`**。  
   - 全是离线逻辑，**不打开抖店页面**，也**不调用 MCP**。

2. 要验收 Feature 能不能在真网上跑通  
   - 打开 **`tests/mcp/README.md`** 里的表格，进对应的 **`tests/mcp/features/<id>.md`**。  
   - 在 Cursor 启用 **`user-playwright`**，按文档操作；结论写到 **`.data/mcp-session-records/`**（模板 **`docs/script/mcp-session-record.md`**）。

---

## 举个例子：「判断网址是不是登录墙」

业务里有个函数 **`isLikelyFxgLoginWall(网址)`**：猜这是不是登录相关拦截页。

1. **`tests/pure/login-wall-cases.ts`** 装了很多「网址 + 期望 true/false」。  
2. **`npm run test`** 里的离线脚本会加载 **`dist/`** 里编译后的同一实现，逐条核对。  
3. **不需要**你再写 `*.spec.ts`。

---

## 再举一个：「环境变量配没配齐」

**`isPasswordLoginConfigured()`** 问密码登录开关和邮箱密码齐不齐。测试要在**干净子进程**里灌 env，避免被本机 `.env` 污染——逻辑仍在 **`tests/support/`**，由 **`verify-offline.ts`** 调用，与以前 Playwright unit 行为一致。

## 一句话收尾

**离线对齐靠 `npm run test` + `verify-offline.ts`，真网靠 `tests/mcp/features/*.md` + Playwright MCP；`pure` / `support` / `actions` 仍是配套物料，不再有 `tests/specs/**/*.spec.ts`。**
